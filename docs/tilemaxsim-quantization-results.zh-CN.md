# TileMaxSim 量化、池化与融合算子消融实验报告

## 总览

### 结论

本实验在同一份冻结的视觉张量评测集上，对精确 FP16 TileMaxSim、token
池化、INT8、FP8、PQ、残差 PQ（RPQ）、OPQ、融合 ADC，以及这些策略的合法组合
进行了 27 组真实 GPU 对照。

最重要的结论如下：

1. **需要尽量保持召回时，优先考虑 INT8 或 FP8。** 两者的 Recall@10 均与精确
   FP16 相同（0.7346），存储约为 FP16 的 50.3%，端到端平均延迟分别快 1.85 倍
   和 1.93 倍。当前标量融合 kernel 仍未调优，不能据此宣称融合版本一定更快。
2. **质量、速度和容量的推荐折中是 `pool4-normalized-fp16` 或
   `pq-m32-b8`。** 前者以 25% 存储、4.66 倍加速取得 0.7160 Recall@10；后者以
   5% 存储、9.65 倍加速取得 0.7037 Recall@10。
3. **极限压缩的较均衡方案是 `pool2-normalized-opq-rpq2-m16-b8`。** 它只使用
   约 2.51% 的存储，平均延迟 405.80 ms、加速 25.83 倍，Recall@10 为 0.6914。
4. **最激进组合不适合作为默认值。** `pool4-normalized-opq-rpq3-m16-b8`
   把存储进一步降至 1.88%，但 Recall@1/5/10 相对精确 FP16 分别下降
   16.67、14.20 和 5.56 个百分点；端到端延迟与两阶段方案几乎相同。
5. **PQ/RPQ 的 fused ADC 已证明有明确价值。** `pq-m16-b8` 的融合版本在召回
   完全一致时比解码后执行 FP16 TileMaxSim 快约 6.00 倍；RPQ2 融合版本快约
   3.97 倍。
6. **显存不足时系统可以正确流式执行，但本报告不是生产容量承诺。** 超大文档按
   query-token 最大值进行数学等价的分块合并；最终实验在共享 RTX 4090 上运行，
   因此应重视同轮相对结果，不应把绝对延迟直接外推到其他硬件或并发负载。

### 推荐配置

| 目标 | 推荐策略 | Recall@10 | 平均延迟 | 相对加速 | 存储比例 |
| --- | --- | ---: | ---: | ---: | ---: |
| 召回优先 | `fp8-e4m3` / `int8` | 0.7346 | 5,435.79 / 5,679.79 ms | 1.93x / 1.85x | 50.3% |
| 高质量通用 | `pool4-normalized-fp16` | 0.7160 | 2,251.07 ms | 4.66x | 25.0% |
| 高压缩通用 | `pq-m32-b8` | 0.7037 | 1,086.56 ms | 9.65x | 5.0% |
| 极限压缩折中 | `pool2-normalized-opq-rpq2-m16-b8` | 0.6914 | 405.80 ms | 25.83x | 2.51% |
| 仅容量优先 | `pool4-normalized-opq-rpq3-m16-b8` | 0.6790 | 405.97 ms | 25.81x | 1.88% |

这里的“存储比例”以精确 FP16 文档张量为 100%，包含对应编码数据，不代表数据库
整库、索引、缓存元数据或运行时 workspace 的总占用。

## 分项报告

### 1. 实验问题与边界

实验回答四类问题：

- token 池化能否以可控召回损失减少 TileMaxSim 的计算量；
- INT8/FP8 能否在接近无损的前提下降低传输与存储成本；
- PQ、RPQ、OPQ 能否提供更激进的容量和延迟收益；
- fused dequant-dot-max 与 fused ADC 是否优于先解码完整 FP16 张量再打分。

本实验只测**视觉张量 TileMaxSim**，明确排除 FTS、图谱、Fact Store、查询扩展、
reranker、业务关键词加权和应用层 ACL。这样可以避免把候选生成质量或业务规则误算成
量化算子的收益。实验没有添加针对评测问题的正则、词表、固定答案或特殊分支。

### 2. 冻结评测契约

- 语料：1,124 份去重文档，共 43,436 页；每页使用 320 维 ColQwen token 张量。
- 查询：81 条严格问题，相关文档标注覆盖全部查询。
- 质量主指标：文档级宏平均 Recall@1/5/10；多相关文档按实际召回比例计分。
- 辅助指标：Hit@K、MRR，以及相对精确 FP16 的 top-10 重合率。
- 性能指标：query preparation、Host→Device transfer、kernel 和端到端延迟。
- 运行约束：固定随机种子；PQ 训练抽样 20,000 行、8 次 k-means 迭代；每个查询
  先预热一次，再记录计时。
- 完整性：43,436 个张量文件均通过全量摘要校验，无缺失、孤儿文件或校验错误。

原始语料、问题文本、张量文件、内部文件路径和生成缓存不随开源仓库发布。仓库只保留
可复现程序、评测契约与聚合结果；用户应使用自己有权处理的数据生成 execution
manifest。

### 4. 标量量化：INT8 与 FP8

INT8 和 FP8 都保持了精确 FP16 的 Recall@10。INT8 的精确 top-10 重合率达到
0.9975，FP8 为 0.9654；这说明 INT8 的排序扰动更小，而本评测集上 FP8 的
Recall@1 略高。两者把编码存储压缩到约一半，因为除了 8-bit token 值，还需要保存
缩放参数和元数据。

分阶段平均耗时如下：

| 策略 | 传输 ms | kernel ms | 端到端 ms |
| --- | ---: | ---: | ---: |
| 精确 FP16 | 9141.26 | 1319.42 | 10480.00 |
| INT8 fused | 4439.29 | 1230.86 | 5679.79 |
| INT8 unfused | 3527.92 | 920.73 | 4470.14 |
| FP8 fused | 4318.57 | 1108.00 | 5435.79 |
| FP8 unfused | 3539.12 | 921.40 | 4482.01 |

本轮共享、低空闲显存条件下，标量 unfused 反而更快。它不表示“融合原则无效”，而是
说明当前 fused scalar kernel 的 tile、访存和 launch 组织尚未达到优化目标。融合
版本能减少完整 FP16 arena 的物化，但在进入生产默认路径前仍需在独占 GPU 上做
Nsight 分析和 kernel autotuning。

### 5. Token 池化

普通二倍与四倍池化都取得 0.6914 Recall@10；四倍池化以约 25% 存储获得 4.41 倍
加速。四倍池化后执行 L2 normalization 把 Recall@10 提高到 0.7160，同时速度提升
到 4.66 倍，是本轮最好的简单策略。

`document-mean-fp16` 虽然极快，但它把整个文档压成一个向量，Recall@10 只剩
0.1728。这说明 late interaction 的 token 级匹配不能用全文均值替代；该项只应作为
消融下界，不应作为检索配置。

### 6. PQ、OPQ 与残差 PQ

PQ 的子空间数决定容量、速度和质量之间的主要权衡：

- `pq-m8-b8` 仅 1.3% 存储，但 Recall@10 为 0.4444；
- `pq-m16-b8` 使用 2.5% 存储，Recall@10 提高到 0.6173；
- `pq-m32-b8` 使用 5.0% 存储，Recall@10 达到 0.7037，并取得本轮最高
  Recall@1（0.3765）；
- 把每个码从 8 bit 降到 4 bit 会明显损害质量，`pq-m16-b4` 的 Recall@10
  只有 0.4444。

残差级数增加后，RPQ3 相对 RPQ2 将 Recall@10 从 0.6420 提高至 0.7037，但存储从
5.0% 增加到 7.5%，速度从 12.18 倍降到 9.09 倍。单独的 OPQ-m16 在 2.5% 存储下
取得 0.6667 Recall@10，优于同容量的普通 PQ-m16。

### 7. 融合 ADC 的收益

| 对照 | 召回变化 | unfused ms | fused ms | fused 加速 |
| --- | --- | ---: | ---: | ---: |
| PQ m16 b8 | 完全一致 | 2016.48 | 336.24 | 6.00x |
| RPQ2 m16 b8 | 完全一致 | 3416.73 | 860.50 | 3.97x |

PQ/RPQ fused ADC 不生成完整解码后的 FP16 文档张量，而是由 query 与 codebook 构造
查找表，再直接按编码累积和执行 token max。因此它同时减少解码算术、中间数据和
显存流量。本轮结果已经支持把 fused ADC 作为 PQ/RPQ 的主执行路径。

### 8. 全策略组合

较均衡的完整组合 `pool2-normalized-opq-rpq2-m16-b8`：

- Recall@1/5/10：0.2346 / 0.5556 / 0.6914；
- 平均延迟：405.80 ms，相对精确 FP16 快 25.83 倍；
- 存储比例：2.51%；
- 分阶段：query preparation 1.62 ms、传输 294.91 ms、kernel 108.59 ms；
- 每个查询平均使用 5 个有界批次。

最激进组合 `pool4-normalized-opq-rpq3-m16-b8`：

- Recall@1/5/10：0.1852 / 0.5432 / 0.6790；
- 相对精确 FP16 分别下降 16.67 / 14.20 / 5.56 个百分点；
- 平均延迟：405.97 ms，相对精确 FP16 快 25.81 倍；
- 存储比例：1.88%；
- 分阶段：query preparation 1.92 ms、传输 314.27 ms、kernel 89.35 ms；
- 每个查询平均使用 4 个有界批次。

激进组合的 kernel 比两阶段组合约快 17.7%，但 transfer 增加，最终端到端延迟没有
改善；同时 Recall@1 再下降 4.94 个百分点、Recall@10 再下降 1.23 个百分点。它只
适合存储容量具有压倒性优先级的场景，不应成为默认推荐。

### 9. 小显存与超大文档调度

本轮统一按约 0.12 GiB 的目标 batch 容量规划。部分单文档的保守工作集估算仍会
超过该目标：

- 精确 FP16 有 14 个 oversized singleton 文档；原生精确 fused kernel 不需要物化
  解码 arena，最大计划工作集约 186.7 MB；
- INT8/FP8 unfused 有 42 个文档进入流式路径，最大保守计划约 280.6 MB；
- PQ/RPQ unfused 有 203 个文档进入流式路径，最大保守计划约 938–943 MB。

流式路径按文档 token 分块，并对每个 query token 合并分块最大值，最后再求和，
因此与整篇文档一次执行的 MaxSim 数学定义一致。它解决的是容量安全和可完成性，
不是保证低延迟；当热点工作集大于 L0/L1 时，L2→L1→L0 的换入换出仍可能主导延迟。

### 10. Pareto 前沿与部署选择

按 Recall@10 和平均延迟观察，本轮前沿依次包含全文均值下界、若干 pool/PQ/OPQ
方案、`pq-m32-b8`、`pool4-normalized-fp16` 和接近无损的 INT8/FP8。实际部署不应
只按一张总表固定全局编码，而应允许知识库或 collection 根据目标选择 profile：

- 高价值、小规模知识库可使用 FP16、INT8 或 FP8；
- 质量敏感且容量有限时使用 normalized pool4 或 PQ-m32；
- 超大规模冷数据可使用 OPQ/RPQ，并把热文档提升到更高质量编码或缓存层；
- 编码 profile、codebook 和模型 contract 必须版本化，禁止不同版本静默混用。

### 11. 局限与后续工作

本报告仍有以下限制：

- 测试使用单台共享 RTX 4090，不是独占、稳频、多轮统计的生产基准；
- 当前结果覆盖 1,124 份文档和 81 条查询，需在更大、更多领域数据上验证置信区间；
- 只测视觉张量打分，不代表端到端 RAG 的候选生成、网络、PostgreSQL 或 LLM 延迟；
- 标量 fused kernel 尚未优于 unfused，需要 profiler 驱动的 tile、流水和批处理优化；
- 尚未完成多请求并发、公平/priority 调度与量化路径组合后的尾延迟测试；
- 尚未验证不同 GPU 架构、PCIe 拓扑、NUMA、多个 SSD 或 GPUDirect Storage；
- OPQ/PQ codebook 的在线升级、灰度切换、回滚和跨版本兼容仍需生产化协议；
- 当前方案是精确范围内打分和压缩，不是张量原生 ANN，不能消除全库算术复杂度。

下一阶段应优先完成：独占 GPU 重复实验与置信区间、Nsight kernel profiling、并发
p50/p95/p99、真实 L0/L1/L2 冷热切换、跨架构验证，以及量化 contract 的在线迁移
与回滚测试。三级缓存的学习型换入换出预测属于后续研究项，必须先与 LRU、TinyLFU、
GDSF 等可解释基线对照，并保留确定性降级路径。
